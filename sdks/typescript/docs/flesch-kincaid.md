# Flesch-Kincaid

The evaluator contracts bind a precomputed `fk_score` into several prompts. Python computes
it with [`textstat`](https://pypi.org/project/textstat/); this SDK computes it with a port of
textstat that returns **the same number, to the last bit**.

```ts
import { fleschKincaidGrade, roundGrade } from './features/flesch-kincaid/index.js';

roundGrade(fleschKincaidGrade(text)); // === round(textstat.flesch_kincaid_grade(text), 2)
```

This document is also the benchmark report: why a port was necessary, what parity required,
and how every JavaScript alternative compares. The results section is generated.

## Why not an existing library

An `fk_score` is not a display value — it reaches the model as a fact about the text, and the
same text must not be graded differently depending on which language ran the evaluator. So the
bar is exact agreement with textstat, not "close enough".

No JavaScript library on npm meets it. The results below cover the four candidates; the
reasons are structural rather than a matter of tuning:

1. **CMUdict, and the right one.** textstat looks syllables up in NLTK's `cmudict` corpus
   (123,455 entries), counting phones that end in a stress digit. Every JS library instead
   *guesses* syllables from spelling. Even the npm `cmu-pronouncing-dictionary` package does
   not help: it is a different corpus (135,155 entries) and disagrees on real words — `nov`
   is 3 syllables in one and 1 in the other.

2. **pyphen for the rest.** About 3% of tokens in our corpus miss CMUdict — numbers, proper
   nouns, typos, and hyphenated compounds, which textstat joins into a single token
   (`AI-powered` → `AIpowered`). textstat counts those as
   `len(pyphen.positions(word)) + 1`.

   pyphen is surprising here: it lists `LEFTHYPHENMIN` and `RIGHTHYPHENMIN` among the header
   lines it *ignores*, and applies its own `left=2, right=2` instead. A port that honours the
   headers — as general-purpose hyphenators such as `hypher` do — finds fewer break points and
   under-counts. Honouring them gave **43.7% disagreement across 141,028 words**; matching
   pyphen's actual behaviour gave **0**.

3. **textstat's sentence rule.** Sentences are `\b[^.!?]+[.!?]*`, and any fragment of two
   words or fewer is then discarded, with a floor of 1. A page of headings therefore counts
   far fewer sentences than splitting on terminal punctuation suggests — which raises
   words-per-sentence, and so the grade. This is the single largest source of divergence.

4. **Unicode-aware regexes.** Python's `\w` and `\b` are Unicode-aware for `str` patterns;
   JavaScript's are ASCII-only *even under the `u` flag*. A sentence beginning with `ß` or `é`
   has no `\b` for JavaScript to match, and silently merges into the one before it. Clean
   prose never exercises this — it only surfaced against deliberately adversarial input.

## Rounding is a separate trap

The contracts say the score is rounded to 2dp. Python's `round()` rounds half to even on the
decimal representation; JavaScript's `Math.round(value * 100) / 100` rounds half up. They
disagree on exact ties:

| value | Python `round(v, 2)` | `Math.round(v * 100) / 100` |
| --- | --- | --- |
| 2.715 | 2.71 | 2.72 |
| 5.805 | 5.8 | 5.81 |
| 18.505 | 18.5 | 18.51 |

Ties are rare but real — 7 of 4,027 values measured while building this. Use `roundGrade()`,
which is `toFixed`-based and matched Python on every value tested.

## The corpus

`tests/unit/features/flesch-kincaid/parity-corpus.json` records textstat's own answers, so
the test suite needs no Python. It is three input classes at once, and they are reported
separately below because they fail differently:

| class | what it is | why |
| --- | --- | --- |
| `fixture-prose` | every fixture text in `evals/` | the texts evaluators are really given; the number that matters |
| `edge-case` | empty, whitespace, punctuation-only, contractions, hyphenation, accents, digits, ≤2-word fragments, 200-char words | each targets one branch of textstat's tokenisation |
| `adversarial` | seeded random interleavings of words, punctuation and non-ASCII | inputs nobody would write, which is how the ASCII `\b` bug was found |

## Licensing: this needs a decision

Exact parity requires shipping two third-party data tables, and one of them is not MIT.

`data/hyphenation-patterns.ts` is `hyph_en_US.dic` copied verbatim from pyphen, which takes
it from the LibreOffice dictionaries repository. Those are distributed under a **GPL 2.0+ /
LGPL 2.1+ / MPL 1.1 tri-licence**; this SDK uses the **MPL 1.1** option, which is file-level
copyleft — that module stays MPL 1.1 and keeps its notice, while the rest of the SDK stays
MIT. See `THIRD_PARTY_LICENSES.md`. **This should be signed off before the SDK is published
again.** (CMUdict, the other table, is BSD-style and needs only attribution.)

The patterns are not decoration. Measured over the same corpus, dropping them and falling
back to a heuristic for the ~3% of tokens CMUdict misses:

| syllable fallback | fixture-prose exact | mean abs. err | worst |
| --- | --- | --- | --- |
| pyphen patterns (current) | **100%** | **0.0000** | **0.0000** |
| vowel-group heuristic | 30% | 0.5678 | 2.484 |
| `syllable` package | 31% | 0.3262 | 1.242 |

So without them there is no parity claim — only an implementation that happens to be
somewhat better than the alternatives. The choice is exactness versus an MPL 1.1 file, and
it is a licensing call rather than a technical one.

## Reading the results

The exactness column is the one that matters for a contract: an implementation is a drop-in
for textstat only at 100%. The tolerance columns are there to say how wrong the others are in
terms someone can act on — a grade-level error of 1.0 is a school year.

Note that the component table explains the aggregates. A library can be close on the grade
while being wrong about every count, because three counts feed one formula and errors cancel;
conversely `text-readability` tracks textstat's word count well and still diverges, because
its sentence and syllable counts do not.

The `adversarial` class is not a fair test of libraries that never claimed to handle it, and
it is not evidence that they are unfit for their own purposes. It is here because parity is a
claim about *all* inputs, and it caught a real bug in this port.

## Regenerating

```bash
pip install textstat pyphen        # ground truth and its data
npm run generate:fk-data          # syllable table + hyphenation patterns
npm run generate:fk-corpus        # re-records textstat's answers
npm test                          # parity assertions
npm run benchmark:fk              # rewrites the results section above
```

The two data modules under `src/features/flesch-kincaid/data/` are generated and checked in,
so installing the SDK needs no Python. They are parsed lazily on first use.

## Scope

Flesch-Kincaid and the counts behind it, `en_US` only. There is no Flesch Reading Ease,
Gunning Fog, SMOG, Dale-Chall or Coleman-Liau here, and adding one means proving its parity
the same way. The intention is to extract this into a standalone package once it has run in
anger for a while.
